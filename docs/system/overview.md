# System overview

WebOS is a desktop environment that runs as a single-page Svelte 5 app, hosted statically on GitHub Pages. A kernel builds a fixed set of services (windows, files, apps, settings, session, ...) before anything renders. The shell (desktop, window manager, taskbar, toasts, dialogs) is a set of Svelte components that read those services. Apps are lazily loaded components that run inside windows and talk to the OS through the same services plus a per-window app context. There's no backend. Everything persistent lives in the browser: OPFS (user files plus OS config and state in `/etc` and `/var/lib`), localStorage (app storage only) and the service worker cache.

This page covers the CURRENT code. For intent and history, see [ADRs](../adrs/README.md). For where code goes and naming, see [CONVENTIONS](../CONVENTIONS.md).

## Layers

```
┌──────────────────────────────────────────────────────────────────┐
│ Apps            src/lib/apps/{system,user}/{id}/                 │
│                 define_app() manifest + .app.svelte, both lazy    │
│                 get_app_context() → window handle, storage handle │
├──────────────────────────────────────────────────────────────────┤
│ Shell           src/lib/core/components/                         │
│                 os.svelte → platform shell (desktop, mobile or    │
│                 solo), update overlay                             │
├──────────────────────────────────────────────────────────────────┤
│ Services        src/lib/core/api/services/{name}/                │
│                 settings windows files version notifications      │
│                 dialogs apps desktop session clipboard ui shell   │
│                 shortcuts tasks backup extract ai speech router   │
├──────────────────────────────────────────────────────────────────┤
│ Kernel          src/lib/core/api/kernel/                         │
│                 registry, dependency order, init / shutdown       │
└──────────────────────────────────────────────────────────────────┘
        browser: localStorage · OPFS · Cache Storage / service worker
```

Each layer only reaches down. Shell components and apps get services with `kernel.service<T>("key")` inside `$derived` (see [kernel.md](kernel.md#consumer-rules)). Services get their dependencies the same way. The exceptions to "only reaches down" are services importing what they hand to DialogsService. AppsService imports the app glob (`$lib/apps`) and lazily imports `open-with-dialog.svelte`. DialogsService (`save-changes-dialog.svelte`) and VersionService (`intro-dialog.svelte`) lazy-import theirs the same way. BackupService lazy-imports `confirm-dialog.svelte` with the rest of its restore code. A few stay eager: SessionService's Restore dialog (boot shows it), DialogsService's `context-menu.svelte`, ShellService's `confirm-dialog.svelte` and the shortcuts command's `shortcuts-dialog.svelte` (`shortcuts/shell-run.ts`).

## Boot sequence

1. **`index.html`** paints a fixed full-screen `#splash` (Brand Dark `#17252c`, `/logo.svg`, and a progress bar with a `Loading` label under it) and an empty `#app`. Body background is hardcoded to the same colour, so nothing flashes before the theme loads. An inline script in `<head>` defines `webos_load_analytics()` (ADR-070) and calls it only when the mirrored answer (`localStorage` `webos.analytics`) is `allowed`. The loader creates `gtag` once: Consent Mode with `analytics_storage` granted and ads denied, then `config` with the page location stripped of hash and query, then the async `gtag/js`. Unasked and declined visitors load nothing and send nothing. The script returns early in dev (`%DEV%`) and on localhost, so neither the loader nor `gtag` exists there. In a production build, vite-plugin-pwa also injects `registerSW.js`, and a local plugin in `vite.config.ts` adds `<link rel="preload" as="font" crossorigin>` for the hashed `InterVariable` woff2 (ADR-036).
2. **`src/boot.ts`** is the page's entry (ADR-067, [compat](compat.md)). It parses the UA, runs every probe in `core/compat/features.ts` (scoped to the app of a `#/solo/` link), and imports `main.ts` when nothing is missing or outdated beyond the `webos.compat.dismissed` set; otherwise it lazily draws the browser support warning over the splash and imports `main.ts` on Continue. In a production build `index.html` modulepreloads `main.ts`'s chunk, `core` and `preload-helper` and preloads the stylesheet, so they download alongside the entry.
3. **`src/main.ts`** imports `app.css` and `App.svelte`, then imports `kernel` from `src/lib/core/api/index.ts`. Evaluating that barrel creates the `Kernel` singleton, or reuses `window.kernel` (see [Debug handle](#debug-handle)). No app manifest loads at boot (ADR-077): AppsService's `init()` reads the installed apps' entries from `/var/lib/apps/catalogue.json` (the full `store/catalogue.json` on a release's first boot), and each installed app's manifest chunk loads after first paint ([apps](services/apps.md#catalogue-adr-077)).
4. **`await kernel.init(on_step)`**, in parallel with `load_shell(kernel.platform, kernel.mode)`, which downloads only this platform's shell chunk, or the solo shell for a `#/solo/` link (ADR-047). `init()` registers the default services (`init.ts`, which `import()`s only this platform's `windows`, `desktop`, `extract` and `ai` classes and the `speech` class, and the solo `apps`, `session` and `version` in solo mode), resolves dependency order, then constructs each service and awaits its `init()`, one at a time. Before each one, `on_step` moves the splash bar and sets its label, and starts warming chunks the first screen needs: after `desktop`, the widget components on the desktop; SessionService warms the saved session's app components itself ([kernel.md](kernel.md#boot-progress)). The actual order is `files → settings → windows → notifications → dialogs → apps → desktop → session → extract (desktop) → clipboard → ui → shell → shortcuts → tasks → backup → ai → speech → router → version` (see [kernel.md](kernel.md#init-order)). FilesService's `init()` builds the OPFS hierarchy (`/home` with `Desktop`/`Documents`/`Downloads`, `/etc`, `/var/lib`, `/tmp`), migrates a pre-hierarchy flat root into `/home` once, and empties `/tmp` ([files](services/files.md#hierarchy)). SettingsService's `init()` reads `/etc/settings.json` (importing and removing the legacy localStorage `webos.settings`, or the v0 React `settings` key, once) and starts the effect that writes theme tokens to `<html>`. DesktopService's `init()` lists `/home/Desktop`, reads `/var/lib/desktop/layout.json`, seeds shortcuts on first boot (v0 React pins if present, else two defaults), and starts watching the folder's revision ([desktop](services/desktop.md#lifecycle)). SessionService's `init()` reads `/var/lib/session/session.json`; if it holds windows, it requests the restore dialog without awaiting it, so the dialog appears right after mount and windows are restored only if the user picks Restore ([session](services/session.md)). VersionService's `init()` reads `/var/lib/version/state.json`: no file loads the introduction's chunk and requests the full-screen introduction (above Restore), an older seen release toasts "Updated to vX" ([version](services/version.md#release-notes-and-introduction)). That's async OPFS work on the boot path, and no OPFS means no boot. The splash is still showing.
5. **`mount(App, { target: #app, props: { shell }, intro: true })`**. `App.svelte` renders `web-os.svelte`, and that renders `os.svelte`, which renders the loaded platform shell and the update overlay. Every service exists by now, so `kernel.service()` can never throw during render.
6. **`#splash` is removed** right after `mount()` returns.
7. **Shutdown hooks**: `pagehide` without `event.persisted` calls `kernel.shutdown()`. A bfcache-persisted pagehide keeps the services alive. HMR dispose unmounts the app and shuts the kernel down.

If `kernel.init()` throws (a service `init()` rejects, a dependency is missing, or there's a cycle), the kernel tears down the services that already initialized and rethrows. `main()` rejects, logs `Failed to initialize application:`, and `show_boot_error()` appends `WebOS failed to start: <message>` to the splash in the Brand Dark error colour. Nothing mounts. See [kernel.md](kernel.md#failed-init).

`App.svelte` also imports `./app.css`, which `main.ts` already imports. The duplicate is harmless.

## Shell mount tree

```
App.svelte
└─ web-os.svelte
   └─ os.svelte                       renders the platform shell main.ts loaded (ADR-016, ADR-036)
      ├─ solo/solo-shell.svelte       a `#/solo/` link on any platform: one app, full page, see shell/solo.md
      ├─ mobile/mobile-shell.svelte   phones and tablets, see shell/mobile.md
      │  └─ … + its own dialogs/dialogs-host.svelte (anchored="sheet")
      ├─ desktop-shell.svelte         grid; layout follows settings.taskbar.position
      │  ├─ desktop/desktop.svelte
      │  │  ├─ wallpaper.svelte
      │  │  ├─ desktop-widget.svelte  (per widget item)
      │  │  └─ desktop-item.svelte  (per grid cell) → desktop-item-face.svelte
      │  ├─ window-manager/window-manager.svelte
      │  │  └─ window/window.svelte  (per open window)
      │  │     ├─ window-titlebar.svelte
      │  │     ├─ window-content.svelte  → lazy app component
      │  │     └─ window-sheets.svelte   → this window's dialog sheets (ADR-025)
      │  ├─ notifications/toast-area.svelte → notification-item.svelte
      │  ├─ taskbar/taskbar.svelte
      │  │  ├─ start-menu.svelte → start-menu-popover.svelte → brand/logo-lockup.svelte, command-mode.svelte
      │  │  ├─ taskbar-item.svelte  (per window)
      │  │  ├─ terminal-button.svelte
      │  │  └─ taskbar-tray.svelte → taskbar-clock.svelte, notifications/notification-list.svelte
      │  └─ dialogs/dialogs-host.svelte  (after the grid; native <dialog>)
      │     └─ (component from DialogsService: open-with-dialog.svelte, restore-session-dialog.svelte, ...)
      └─ update/update-overlay.svelte
```

`os.svelte` gets the shell as a prop: `main.ts` awaits `load_shell(kernel.platform, kernel.mode)` (`components/platform-shell.ts`, the one shell branch: solo first, then platform) alongside `kernel.init()`, so only the shell this page needs downloads.

The desktop, window manager, a live wallpaper's overlay layer (ADR-057, only while one is active) and toast area share one grid cell, stacked with z-index in that order. The taskbar gets the other cell. The `ov()` maps in `desktop-shell.svelte` pick the cells from the taskbar position. The grid itself paints `background-darkest`, so the floating taskbar's transparent strip shows the same shade as the desktop. Details are in [shell/](shell/).

## The barrel and the circular-import rule

`$lib/core/api` (`src/lib/core/api/index.ts`) re-exports `./kernel`, `./services` (each service's `index.ts`, which exports types plus a few pure values like `TaskbarPosition`, `THEME_PRESETS` and `define_app`), and `./type`. Its default export is the kernel singleton.

Until ADR-077 stage 2, evaluating the barrel caused this import cycle:

```
api/index.ts → kernel/kernel.svelte.ts → kernel/init.ts → services/apps/service.svelte.ts
  → $lib/apps (import.meta.glob, eager) → every {id}/index.ts manifest → $lib/core/api   ← still initializing
```

AppsService no longer imports `$lib/apps`: a build loads manifests by URL after boot, and the dev server and tests import the glob from `init()`, after the barrel has finished. The cycle is gone; the rule that **a manifest imports only types and hoisted functions from `$lib/core/api`** stays until it's lifted on purpose. See [CONVENTIONS → Apps](../CONVENTIONS.md#apps) and [manifest](apps/manifest.md#the-import-rule).

## Debug handle

`src/lib/core/api/index.ts` stores the singleton on `window.kernel` and reuses an existing `window.kernel` on re-evaluation. This keeps one kernel across HMR, and it also gives you a console handle:

```js
kernel.services                       // SvelteMap of live services
kernel.service("windows").to_string()
```

Boot logs nothing on success. The Kernel system app lists `kernel.services` in the UI.

## Build & deploy

- `vite.config.ts` sets `base: "/webos/"`: the site is the GitHub Pages project site `lilbunnyrabbit.github.io/webos/`. Dev serves under the same path (`localhost:5173/webos/`). Vite rewrites `index.html` asset URLs, the PWA manifest gets `scope` and `start_url` `/webos/`, and the SW registers at `/webos/sw.js`. Runtime URLs go through `import.meta.env.BASE_URL`: `version.json`, the `store/` files (`catalogue.json`, `icons.svg`, `changelog.json`), the app files StoreService downloads, links (`route.ts`) and the compat screen's logo.
- `.github/workflows/deploy.yml` runs on every push to `master` (and manually). Job `fork` deletes `src/lib/apps/user`, then runs `bun run check` → `bun run test:unit` → the browser tests of `src/lib/core`, `src/lib/kit` and `src/lib/apps/system` (Playwright Chromium installed on the runner; core tests use the stand-in apps in `services/apps/test-apps.ts`, never a user app) → `bun run build`: a fork that keeps only core must still work. Job `deploy` waits for it, then runs Bun install → `bun run check` → `bun run test:unit` → `bun run build` → `bun run budget` → upload `dist/` → `actions/deploy-pages`. A type error, a failing unit test, a broken fork or an entry chunk over budget blocks the deploy.
- Dependencies (ADR-045): Bun workspaces over `src/lib/apps/*/*` with the isolated linker (`bunfig.toml`). Core packages sit in the root `package.json`; an app that needs a package declares it in its own `package.json`, and only that app's files can resolve it. One root `bun install` installs everything, so CI needs no extra step, and the fork test drops user apps' packages with their folders.
- Boot budget: `scripts/boot-budget.ts` gzips the module scripts `dist/index.html` loads, plus the chunks it preloads (`modulepreload`), and fails over 167.2 KB gz (`BUDGET_BYTES`, lowered on 2026-10-26, see the end of this item). History: 166.9 KB at 1.0 under a 180 KB budget, raised to 190 on 2026-10-17 for app wave 7. 170.5 KB gz at 3.21.0: entry 25.9, `core` 131.9, `app-boot` 12.7; 171.6 at 3.26.1; 189.0 at 3.58.0 (`app-boot` 13.6), 182.0 at 3.59.0 once app icons became files (`app-boot` 6.9, ADR-066). 189.3 at 3.60.0 with the browser support gate (ADR-067): entry (`boot.ts` and the list) 7.0, `preload-helper` 0.8, `main` 30.8, `core` 143.8, `app-boot` 6.9; `main.ts`'s chunks are counted through the `modulepreload` links `preload_main_plugin` adds. Raised to 215 on 2026-10-24 when icons and app text went back into boot at the owner's call ("it's just text and icons"): 210.1 at 3.61.0, `app-boot` 13.7 with the icon components (ADR-066 reverted), `app-meta` 13.6 preloaded (ADR-049 revision). `index.html` (with the import map) isn't counted. Raised to 218 on 2026-10-25 at the owner's call when Color Tools and the four colour games (ADR-071) took it to 216.0 at 3.70.0 (`main` 32.9, `core` 145.9, `app-boot` 14.4, `app-meta` 14.8); Raised to 219 on 2026-10-26 at the owner's call when Speech, Docs and Paste to Open (ADR-074–076) took it to 218.16 at 3.73.0; the boot-weight pass is next. 218.6 once every manifest got its own chunk (ADR-077 stage 2, build side). Lowered to 167.2 on 2026-10-26 when boot stopped importing manifests and app text (ADR-077 stage 2, runtime): 164.2 KB gz at 3.74.0 (entry 7.3, `preload-helper` 0.8, `main` 12.9, `core` 143.2), `app-boot` and `app-meta` gone; the budget is the reading plus 3 KB. Boot now grows with core, not with the number of apps.
- Chunks (ADR-036 revision 2026-10-21). A Rollup chunk's hash covers the names of the chunks it imports, so whatever every app imports must not name anything that changes often. `vite.config.ts` `manualChunks`:
  - `core`: the boot graph minus anything that reaches, statically or through `import()`, app code or the dev glob (`src/lib/apps/index.ts`, reached by nothing in a build). The build stamp (`services/version/build-info.ts`, the only reader of `__VERSION_INFO__`) and `changelog.ts` are in no chunk at all since 2026-10-27: the build fails if one holds them (`RELEASE_MODULES`, below). `tooling/vite-core-chunk.ts` computes it, following imported names through barrels, because Rollup adds every static dependency of a manual chunk's modules to it and a whole barrel would pull the kit in. For the same reason `phosphor_imports_plugin()` (`tooling/vite-plugin-phosphor.ts`) rewrites `import { X } from "phosphor-svelte"` to one import per icon file at build time.
  - `app-boot` and `app-meta` are gone (ADR-077 stage 2): what a manifest imports lands in its manifest chunk or a chunk it shares with its component, and every `meta.ts` in a small chunk of its own that nothing loads at runtime.
  - The `main` chunk (the entry until ADR-067 put `boot.ts` in front of it) keeps `main.ts` and `init.ts`; until 2026-10-27 it also held AppsService, VersionService and BackupService, which read the build stamp, and changed every release. `main.ts` calls `register_default_services()` before `kernel.init()`, so the kernel never imports them.
  - Measured with `dist/sw.js`'s precache list (731 entries, 10.7 MB): a rebuild with no change renames 16 files (0.32 MB), a one-line app change 17 (0.33 MB), a version bump plus a changelog edit 17 (0.39 MB). Before: 606 of 765 (5.65 MB) in all three cases. The 16 are the entry, `index.html`, `changelog` (on a version change), the two solo services and 12 app chunks that import their own `index.ts` manifest (csv-viewer, text-editor, media-preview and others); moving what they import out of `index.ts` would drop them too. Since the import map below, a change in `core` no longer renames the apps.
  - `preload-helper` (ADR-067): Vite's preload helper is a manual chunk of its own. Every chunk with a lazy import uses it; in `core`, the `boot.ts` entry would have imported all of core before the browser check.
  - Import map (`tooling/vite-plugin-import-map.ts`, build only; ADR-036 revision 2026-10-21, follow-up). Every chunk imports `core` as the bare specifier `@webos/core` (rewritten in `renderChunk`, before Rollup hashes, so no chunk's hash covers core's), and a `<script type="importmap">` injected into `dist/index.html` maps it to `assets/core-<hash>.js`. Core's lazy imports and its `__vite__mapDeps` preload list name their targets as `@webos/<name>.<id>.js|css` (`<id>`: a hash of the chunk's source path(s) relative to the root, Rollup's `\0` and any query stripped by `module_identity()` so two checkouts give the same id, stable across builds), resolved through the same map with `import.meta.resolve` (Vite's `experimental.renderBuiltUrl`); other chunks' preload lists name core and its CSS the same way. Core is renamed after the bundle is final, from a hash of its final code, and `index.html` is patched to match, so a hashed precached file never changes content under one name. `index.html` and core always change together, and the service worker precaches both. The map has ~87 entries (~6 KB). `bun dev` is untouched.
  - Measured against a rebuild of the same tree (742 entries): a one-line change in a core module (`turrets/options.ts`) renames 17 files (0.76 MB, core included), a markup change in a chunk core lazy-loads (`turrets-overlay.svelte`) 17 (0.34 MB, core unchanged), a one-app change 17. Before the map: 583, 583 and 17 (5.98 MB for the first two).
  - Keep it that way: a core module that imports `$lib/apps` drops out of `core` into the entry along with everything that imports it, and boot and update size both grow. One that reads `__VERSION_INFO__` or imports `changelog.ts` fails the build: the running release comes from the catalogue (`apps.header`) and the notes from `store/changelog.json` ([version](services/version.md#public-api)).
- Offline lists (ADR-065, ADR-077, `tooling/vite-plugin-offline.ts`, build only). In `writeBundle` it walks the chunk graph from `index.html` and the entry and writes `dist/offline/core.json` (everything boot reaches without entering an app's lazy code: the chunks above and the fonts) and `dist/offline/{id}.json` for every app, system apps included (what its manifest's `import()`s reach, minus core and the files other runtime rules cache), each `{ build, files }`. The service worker precaches only `core.json`'s files; [StoreService](services/store.md) downloads an installed app's list when it's installed and after every update. The build stamp is computed once in `vite.config.ts` (`get_version_info`) and shared by `version_plugin` and the lists. The runtime cache is one `webos-assets` for every release (ADR-077 stage 3). Measured at 3.58.0: 305 precache entries (4.2 MB) instead of 844 (12.4 MB); at 3.74.0, with system apps out of core (ADR-077 stage 1): 202 entries (2.7 MB) and 105 app lists.
  - **Content** (ADR-077). A chunk whose every module was imported with the `content` query parameter (`?raw&content`; `CONTENT_QUERY` and `is_content_chunk` in the plugin) is content: the walk doesn't enter it, so it's in no install list and not in core. Each app's list file names the content its files import apart, `{ build, files, content }`, and the catalogue entry carries the same `content`. The app hash covers `files` and `content`, so a changed page is a new version of the app. At runtime a content file loads like any lazy chunk and the `assets/` runtime rule caches it. Docs' markdown pages are the one user today (152 files, 792 KB gz), shared by Kernel through `has_page`: Docs installs 20 files (59 KB gz, was 172 and 851 KB), Kernel 6 (11 KB, was 158 and 803 KB). Settings' What's new roadmap imports `ROADMAP.md?raw` without the query, so it stays installed with Settings.
- App catalogue (ADR-077 stage 2; `tooling/vite-plugin-catalogue.ts`). AppsService reads it ([apps](services/apps.md#catalogue-adr-077)): boot only the installed apps' slice in OPFS, `catalogue()` the full file, `load(id)` an app's manifest chunk by URL.
  - **Manifests at build time.** In `buildStart` the plugin starts a second, bare Vite server (no config file: `svelte()` plus the build's aliases and defines) and loads every `src/lib/apps/{system,user}/*/index.ts` with `ssrLoadModule`, then each manifest's `meta()` and `changelog.ts`. Only those two folders: anything else under `src/lib/apps/` never reaches the catalogue. A manifest that touches the DOM at module level fails the build ([manifest](apps/manifest.md#node-safe)). Takes ~7 s, in parallel with bundling.
  - **Manifest chunks.** Every `index.ts` is emitted as an entry of its own (`assets/{id}.manifest-<hash>.js`, `preserveSignature: "strict"`), its icon and props inside or in a chunk shared with its component; a facade when the app's component imports its own manifest. Real entries, not implicit ones after `main`: Rollup ordered 105 implicit entries as they finished resolving, which reshuffled core's mangled export names between two builds of the same tree. `is_manifest_chunk(name)` (the `.manifest` suffix) keeps them out of what the offline lists and `preload_main_plugin` treat as boot. Each is the first file of its app's list (`files`), so installing downloads it; not precached.
  - **`dist/store/catalogue.json`**: `{ version: 1, core, build, release, commit, branch, apps }`, apps sorted by id; `build` is the build stamp, which a page compares with its own before running an entry's code. `release`, `build`, `commit` and `branch` are also how a page knows which release it runs (VersionService `info`): nothing about the release is in the bundle. Each: `id`, `name`, `category`, `system`, `version`, `hash`, `manifest` and `entry` (the manifest's and the component's chunk, relative to the base), `files` (exactly `offline/{id}.json`'s list, read after that plugin writes it), and when present `associations`, `tools`, `description`, `keywords`, `pitch`, `authors` (from `meta`), `defaults`, `replaces`, `restore: false`, `daily_rank`, `widget_size`, `default_widget`, plus flags for what needs the manifest's code: `daily` (props take `daily`, Game Hub), `widget`, `highlights`, `preview`, `shell`, `badge`, `on_fire`, `on_uninstall_data`. The entry shape and `manifest_data()` live in `src/lib/core/api/services/apps/catalogue.ts`, which the plugin imports, so the runtime's dev and test path describes apps with the same function. Data only: functions dropped, sets as arrays. 110 KB raw, 30.5 KB gz for 104 apps at 3.73.0.
  - **`dist/store/icons.svg`**: one `<symbol id="{app id}" viewBox>` per app, each manifest's `icon` component rendered with `svelte/server`. Sizing attributes (`width`, `height`, `aria-hidden`, `class`) go; the `<svg>`'s other attributes wrap the content in a `<g>`. Colours stay `currentColor` and `var(--…)`, so `<svg><use href="store/icons.svg#snake"/></svg>` takes the page's theme. 42.8 KB raw, 7.0 KB gz.
  - **`dist/store/changelog.json`**: `changelog.ts`'s `CHANGELOG` as JSON (106 KB raw at 3.74.0), at a fixed name, read by VersionService's `load_changelog()`; not precached, cached by the `NetworkFirst` `store/` rule. Authors keep writing `changelog.ts`; the Discord script imports it directly.
  - **Hashes.** Both read text files with every content-hashed file name (`name-HASH8.ext` → `name.ext`) unhashed, so two builds of the same tree hash the same while a file's own change still counts. Nothing else is rewritten: no chunk holds the build stamp (`RELEASE_MODULES`), and replacing it used to rewrite any text that mentioned the release, so Docs, Kernel and Settings (the roadmap says "3.74.0") got a new version on the next release with no change (fixed 2026-10-27). A set is hashed as the sorted list of `unhashed name + sha256(unhashed content)`.
    - **Core hash**: every file in `offline/core.json` (index.html with its import map, the entry, `preload-helper`, `main`, `core` and its CSS, their lazy chunks, fonts: everything boot reaches without entering an app) plus the precached files in `public/` (`sw-notifications.js`). It's what a new service worker would precache, so a different core hash means a full update; the same one means an app-only update, taken without a reload ([store](services/store.md#hot-updates-adr-077-stage-3)). After hashing, the plugin writes it into `dist/index.html` as `<meta name="webos-core" content="…">` (`with_core_meta`, `CORE_META` in `apps/catalogue.ts`): the page reads its own core from there (`running_core()` in `apps/source.ts`; `"dev"` on the dev server), and `index.html` already changes exactly when core does. The hash reads `index.html` before the meta goes in, so the next build of the same core hashes the same. Measured on 2026-10-26: two builds that differ in one user app's source, a `package.json` bump (3.74.0 → 3.74.1, then 3.75.0) and a new changelog release give the same core hash, and a rebuild of one tree gives the same hash; the new release's update downloaded 6 precache files. Measured on 2026-10-27, with the release out of the bundle: build N, then N+1 with a Snake edit, a patch bump and a changelog line, gives a byte-identical `sw.js`, the same 202 precache entries, the same core hash and 0 renamed core files (only Snake's two chunks are new); a core edit on top changes `sw.js` and the core hash.
    - **App hash**: the app's `files` (its manifest chunk included), its catalogue data, its sprite symbol and its `index.ts` source. Internal. The normalizer's version placeholder also hits the version string in bundled docs text: Docs, Settings and Kernel (which bundle `docs/` pages naming the current version) get a new hash in a release whose version they mention.
  - **Versions.** The build fetches the deployed catalogue (`https://lilbunnyrabbit.github.io/webos/store/catalogue.json`, or `WEBOS_PREVIOUS_CATALOGUE`; empty skips it; 5 s timeout). An app whose hash equals the previous entry's keeps its `version`; any other app, and every app when there's no previous catalogue (offline, first deploy, a fork), gets `package.json`'s version. A fetch that was asked for and failed (unreachable, a non-200, not a catalogue) prints a loud `console.warn` saying every app got this release as its version, and the build goes on; `WEBOS_REQUIRE_PREVIOUS_CATALOGUE=1` makes it fail instead (`previous_or_warn`). The deploy workflow doesn't set it yet: the first deploy with a catalogue has no previous one to read.
  - **`version.json`** gains `core` (the core hash) and `notes`: the top changelog release plus every release newer than the previous catalogue's `release`, each `{ version, date, title, changes: [{ kind, text, apps? }] }` ([version](services/version.md#where-the-data-comes-from)).
  - **Dev and tests.** Boot never waits for a built catalogue: `import.meta.env.DEV` code gives AppsService `glob_source()`, which describes the glob with `manifest_data()` ([apps](services/apps.md#catalogue-sources)). The dev server (and Vitest's browser server, which shares the plugins) answers only `{base}store/icons.svg` from `collect_apps()` (the sprite, for apps that aren't installed) and `{base}store/changelog.json` from `changelog.ts`, through its own `ssrLoadModule`, `no-store`; there is no dev `store/catalogue.json`. The first request takes a few seconds. Node tests call `collect_apps(root, load)` with a plain `import()` (`tooling/vite-plugin-catalogue.test.ts` does, checking a symbol per app).
  - Not precached: the service worker's `globPatterns` take `js`, `mjs`, `css`, `html` and `woff2` only. A `NetworkFirst` rule caches `store/` in `webos-store`, so the last catalogue, sprite and changelog answer offline ([store](services/store.md#service-worker)).
- Branches: `master` is this Svelte version. The React version (v0) is frozen on `v0-react`.

### Upgrading from v0 (React)

The origin is shared, so a v0 user's storage is still there on first load. Nothing is lost:

| v0 storage | Becomes | Where |
|------------|---------|-------|
| OPFS root (all files and folders) | `/home/...`; a v0 `Documents` folder is `/home/Documents` | `ensure_hierarchy` ([files](services/files.md#hierarchy)) |
| localStorage `settings` (zustand) | `/etc/settings.json`: taskbar position; theme only if changed from v0's defaults, else Brand Dark | `take_v0_settings` ([settings](services/settings.md)) |
| localStorage `desktop` (zustand) | `.desktop` shortcuts at the same grid cells; pins of apps that weren't ported are dropped | `take_v0_pins` ([desktop](services/desktop.md#behaviour--invariants)) |

Both localStorage keys are removed once read.
