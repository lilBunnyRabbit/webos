# App store: installed = cached, flat boot, app updates without reload
**Date:** 2026-10-26
**Participants:** owner, Claude

## Context
Roadmap line (owner, 2026-10-21): "load apps into cache only when installed, only show installed apps, per-app versions, auto-update when closed".

What exists:
- Installed set (ADR-040, `/var/lib/apps/installed.json`); App Library is the store (Get / Open / Uninstall).
- Apps on demand (ADR-065): precache = core + system apps; user apps cached per build in `webos-assets-{build}`; a separate offline "picked" set in `/etc/offline.json`.
- Import map (3.26.1): chunks import `@webos/core`, an app-only change renames ~17 files.
- Boot loads every app's manifest (`app-boot`, 14.5 KB gz) and text (`app-meta`, 15.3 KB gz) for 90 user + 15 system apps (ADR-049, revision 2026-10-24).
- App chunks import core by minified names (`import{eO as Ze,…}from"@webos/core"`), which change whenever core changes, so an app from build N+1 can't run on core N.
- Last 25 releases: ~7 touched only user apps (3.67.0, 3.66.0, 3.64.0, 3.54.0, 3.51.0, …).

Owner on the pieces: "installed would mean cached which makes more sense. boot doesn't grow per app which makes sense aswell. and update apps without os reload would be amazing." Design all three first, then one ADR each.

## The three pieces
1. **Installed = cached.** OfflineService syncs the installed set instead of `picked`; Get downloads, uninstall drops files no other installed app lists; picked migrates into installed.
2. **Boot doesn't grow per app.** Build writes a catalogue (data per app: id, name, icon, category, associations, text, entry, version). Boot reads installed apps' entries from a cached copy; search's Not installed group, Open with, deep links, intro, App Library and Game Hub read the catalogue.
3. **App updates without reload.** Catalogue carries a version per app (hash of its files) and a core hash. Same core hash: only apps changed, no reload; apps load by URL from the catalogue; open windows keep the old module, badge "Update ready", Restart app. One cache pruned by installed lists instead of one per build. Depends on 2.

## Transition for existing users
The first release with this changes core, so it arrives as a normal full update (overlay, reload). After the reload the tab runs the new model; picked migrates into installed once. A second tab still on the old build follows the old update path and reloads. No hot path exists until both sides speak catalogue.

## Downsides (raised 2026-10-26)
- Two update paths (full, hot) to build and test; more states to reason about.
- Mixed versions in one tab: Snake new, Diff old. A shared lazy chunk can load twice (memory, duplicated module state).
- Two windows of one app on different versions can write the same file in different formats.
- `define_app` / manifest shape change touches every app; icons stop being components unless rendered at build.
- Dev server and tests have no built catalogue: a second, glob-based path for them.
- Not-installed apps in search need the catalogue fetched (network on first use, cached after).
- Installed = cached costs storage and phone data after each update.
- A hot update can't fix core bugs; those still wait for a full update.
- Reverses the ADR-049 2026-10-24 revision; revises ADR-040, 065, 004, 036 and the manifest page.

## Topics discussed

### Round 1 (decided)
- **Catalogue source: the build extracts `define_app`.** Authors keep writing `index.ts` as today; a build step imports every manifest, renders icons and writes `store/catalogue.json`. Runtime loads an app's `index.ts` only when needed. Rejected: split `app.json` + `index.ts` (all 105 apps churn, two files forever); keep boot as is (no boot win, manifest changes still force a reload).
- **One version per app per tab.** Open windows keep the old version; the taskbar shows "Update ready" with Restart app; new windows open the old version until every window of that app is closed. Rejected: new windows on the new version (two versions writing the same files); auto restart (surprising mid-game).
- **Installed apps download right away after an update** (only renamed files, unchanged ones copied). Owner: "not the big loading screen? i would just show loading on the apps that are updating and the notification." Rejected: Wi-Fi only on phones (Chrome-only signal); on first open (installed apps may not work offline).
- **App Library is renamed App Store.** The id stays `app-library` (links, `app launch app-library`). Game Hub stays the games store.

### Round 2 (decided)
- **Boot reads the catalogue slice only; installed apps' code loads in the background.** Owner: "i mean code in the background and the loading state on app". First paint needs no app code; each installed app's `index.ts` loads after it, and its tile shows a loading state until then (badges of Calendar, Kanban and Quick Notes fill in when their code lands). Rejected: awaiting every installed manifest before first paint.
- **Icons for not-installed apps: one SVG sprite** (`store/icons.svg`, a `<symbol>` per app, `<use href>`). Owner: "whatever is best". No `{@html}`; `currentColor` and `var(--primary)` inherit into `<use>`. Installed apps keep their component. Rejected: SVG strings in the catalogue (`{@html}`), a lazy icon chunk per app (~100 requests on first Store open).
- **Running catalogue: `/var/lib/apps/catalogue.json`,** the core hash plus installed apps' entries, written when a sync or hot update is accepted. Boot reads only that, so it stays flat with the app count. The full catalogue is fetched network-first when the Store or search needs it. A restored backup that doesn't match the build re-fetches. Rejected: the whole catalogue in Cache Storage (boot parses every app).
- **Update UI: rings and one toast.** Core change: the overlay waits on core only, then reloads. Installed apps then download with a progress ring on their icons (start menu, taskbar, desktop, Store) and one progress toast. App-only change: no overlay, no reload, rings and toast, then "Snake and 2 more updated" with What's new. Open windows: "Update ready" with Restart app.
- **The update overlay says what's updating** (owner, mid-round: "we can also update the main loading screen to give user more information what is actually updating - since this will be core only changes"). It covers core only now, so it can show from → to version, the release's changelog lines and file progress.

### Round 3 (decided)
- **System apps join the app model, installed by default** (owner: "yea like any other but installed by default"). They leave the precache and sync like user apps, always installed and locked. Precache is core only, so the service worker changes only when core does, and a Settings or Explorer fix hot-updates. Rejected: keeping them in core (every system-app edit a full reload).
- **An app's version is the release it last changed in** (Snake 3.67.0). The build compares each app's file hash with the previous catalogue and keeps the old number when equal. The hash stays internal. Rejected: manual semver per app; hash only.
- **Overlay notes ride in `version.json`:** the poll already fetches it; the build adds the new release's changelog entries and the core hash. Rejected: notes in the catalogue (the poll would fetch the big file).
- **One ADR (077 App Store), three stages, each its own release:** (1) installed = cached and the App Store rename, (2) catalogue, flat boot, icon sprite, overlay notes, (3) hot app updates.

### Round 4 (decided)
- **Store buttons: Install and Open.** Owner: "maybe install and open? try looks like a trial version. this is just full but not cached". Open runs the full app without keeping it. Follows: a file, deep link or announcement opens a not-installed app the same way instead of installing silently (ADR-040 change).
- **The offline logic goes** (owner: "We can then remove the 'offline' logic we have that would just then be installed/not installed?"): `/etc/offline.json`, Settings › Offline, Keep offline, the dimmed offline launcher.
- **OfflineService becomes StoreService (`store`):** catalogue, downloads, versions, update detection, hot swaps, cache, Web Lock. AppsService keeps registry, launch, listings and the installed set. Rejected: folding it into AppsService.
- **An "Update" button in the window** (owner, after the ADR: "window of the app should probably have a 'new version' button or sth"): an open window of an updated app shows it in its titlebar, beside the taskbar's "Update ready"; both run Restart app.
- **Docs follow every stage** (owner: "this will require the docs to update aswell"). The per-stage docs map is in ADR-077 Consequences.

## Key takeaways
- One state per app: installed means listed, downloaded, offline and updated.
- Boot follows installed apps, never all apps.
- Only core changes reload the OS.
