# CI status in WebOS
**Date:** 2026-10-22
**Participants:** owner, Claude

## Context
Owner: "can we show pipeline status in webos or would that requrire a server", then "public token wouldn't be an issue?". No server needed: the repo is public and `api.github.com` answers CORS without a token, 60 calls an hour per IP. A token in the bundle was ruled out: it would be extracted, revoked by GitHub's secret scanning, and its limit shared by every visitor. The workflow is `deploy.yml` with three jobs (fork, deploy, announce). Owner: "put CI status in Settings About".

## Decisions
- **Content:** the newest master run, its state, short sha, title and start time, one chip per job, a link to the run, and whether it is this build or newer. Rejected: run only (can't tell which job failed); last five runs (room, detail only via the link).
- **Fetch:** on opening About and on Refresh; every 30 s while the run is queued or running and About is mounted. Memory only. Rejected: Refresh only (no live progress); a cache in `/var/lib` (persistence for data that goes stale in minutes).
- **Home:** `VersionService.pipeline()`, beside the update check, logic in `version/pipeline.ts`. Rejected: a settings-local `ci.ts` (the owner wanted it in the service).
- **Shell:** `ci status` from the version service, yielding `ci-job` values (job, status, took); clicking a row opens the job.
- Revision note on ADR-004, which had rejected the GitHub API for update detection; that stays on `version.json`.

## Key takeaways
- Two calls per fetch; a 10-minute run polled every 30 s uses about 40 of the 60 an hour.
