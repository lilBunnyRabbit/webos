# Dev-only apps and a bridge to the Claude Code session
**Date:** 2026-10-26
**Participants:** owner, Claude (investigation agent)

## Context
Owner: "can we make 'dev only' apps. like one that comes to mind is icon/graphics generation where i could directly write in the 'app' or whatever and it would send the message to the session i am working in. the apps and calls would be optimized for those", then "this apps would also need to persist hot reloads and not be prompted for 'start fresh' 'restore'". Claude Code features checked against code.claude.com on 2026-10-26 (CLI v2.1.310).

## Findings

### Dev-only apps
App discovery is an eager glob over `system` and `user` (`src/lib/apps/index.ts:6`); the build tooling matches only `(system|user)` (`tooling/vite-plugin-offline.ts:24`, `vite.config.ts`), so a third folder is invisible to precache, offline lists and chunking.
1. **Recommended: `src/lib/apps/dev/{id}/` through a serve-only virtual module** (`apply: "serve"`, `virtual:webos/dev-apps`: the dev glob under `bun dev`, `[]` in the build). No dev byte can reach production.
2. A `DEV`-guarded glob in `apps/index.ts`: lighter, but an eager glob becomes hoisted imports and `define_app` counts as a side effect, so Rollup may keep them (unverified; check with a build and grep). A build test asserting no `apps/dev/` module in `dist` either way.
3. Rejected: a `dev: true` flag on apps in `user/`: the code ships and every consumer needs a filter.

What needs a call: a `dev` manifest field and a launcher Developer section (API shape); tests run with `DEV` true, so five test globs over `apps/*/*` would pick dev apps up (`compat/features.test.ts:5`, `version/history.test.ts:90`, `portfolio/content.test.ts:11`, `apps/sentence.browser.test.ts:9`, `ask/catalogue.browser.test.ts:10`); ADR-077's catalogue must glob `{system,user}` only (the stage 2 build agent was told on 2026-10-26). Dev runs on `localhost:5173`, its own origin, so its OPFS, installed set and session never reach production. Dev-app commits never touch the changelog, `package.json` or the compat list. One `docs/system/dev-apps.md` page.

### Bridge: browser app ↔ live session
1. **Recommended: a Claude Code channel** (an MCP server that pushes into the session; research preview). Launch `claude --dangerously-load-development-channels server:<name>` with the server in `.mcp.json`; it reaches an idle session and queues while busy. Replies are ordinary MCP tools on the same server. Gotchas: needs a relaunch; pin `@modelcontextprotocol/sdk` 1.x or `MCP_PROTOCOL_NEGOTIATION=legacy`; a new dev dependency. https://code.claude.com/docs/en/channels.md, https://code.claude.com/docs/en/channels-reference.md
2. **Mods** (plugin JS module): the only option that attaches to an already running session; polls the dev server and submits prompts when idle. Unclear whether its fetch may reach localhost; lives in `~/.claude`. https://code.claude.com/docs/en/plugins/mods/overview.md
3. **Monitor + curl:** zero install, good for a spike; Claude starts the watch and it expires (30 min max).
4. Hooks with `asyncRewake`: one-shot, no reply path.
5. Rejected: the cross-session inbox socket (wire format undocumented), `claude -p` / SDK resume (separate process), Remote Control (no local API).

Wiring (channel): the app sends over Vite's HMR websocket (`import.meta.hot.send`), with no HTTP endpoint, CORS or token in the bundle; a serve-only Vite plugin forwards to the channel server on 127.0.0.1 with a shared secret from a gitignored file; tool calls come back over the same path (`import.meta.hot.on`); files the session edits show through ordinary HMR. No session connected: the app shows an offline state. Unverified: how Vite's websocket rejects cross-origin pages.

### First app: icon workbench
Pick an app; its `icon.svelte` previews at taskbar, launcher, desktop and Store sizes in both themes beside neighbouring icons; a prompt sends `{app_id, request, sizes, icon path}` with the brand rules as doc paths; candidates come back as SVG into the same grid; comment or Accept. **Accept sends a message and the session edits `icon.svelte` itself** (reviewable, through permissions, shown by HMR); a dev middleware that writes repo files was rejected as an arbitrary-write endpoint. Calls: typed inbound events (`kind=icon_request|feedback|accept`, `app_id`, `request_id`) and tools `show_candidates`, `reply`, `done`; standing rules in the server's `instructions`.

### Surviving hot reloads, no Restore prompt
Today a `.svelte` edit hot-swaps in place (local state resets); an edit to an app's `index.ts`, `meta.ts` or any core service reloads the page (`main.ts:87` disposes but never accepts), and boot always asks Restore (`session/service.svelte.ts:106`).
1. **Recommended: silent restore under `bun dev`,** gated on `import.meta.env.MODE === "development"` (not `DEV`, which vitest also sets), with `?restore=ask` and `?fresh` escapes.
2. Silent restore for dev-app windows only: still prompts whenever another window is open.
3. **Recommended alongside 1: dev-app state in `storage.window()`,** saved with the window, survives HMR remounts and reloads. Conversation history stays in the bridge and replays on reconnect.
4. `import.meta.hot.data`: survives HMR only, boilerplate per module.
5. Fewer full reloads by re-registering manifests on HMR: architectural, collides with ADR-077's catalogue; deferred.
Svelte 5's exact HMR state behaviour is unverified (the agent's source was weak).
